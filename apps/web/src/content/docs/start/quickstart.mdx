import { Aside, FileTree, Steps } from '@astrojs/starlight/components'

<Aside type="caution">
The package is not on npm yet, so `npm i -D loclizr` fails until the first release. Inside this
repository it installs from the workspace, the way `examples/vite-react` declares
`"loclizr": "workspace:*"`. Everything after the install step was run as shown against the CLI
built from this repository, and the output is pasted rather than typed.
</Aside>

<Steps>

1. ### Install, then initialise

   ```bash
   npm i -D loclizr
   npx loclizr init
   ```

   ```txt frame="terminal" title="npx loclizr init"
   wrote loclizr.config.ts
   wrote locales/en.json

   Install loclizr, which loclizr.config.ts imports:

     npm i -D loclizr

   Add these scripts to package.json:

     "prepare": "loclizr build --no-fail",
     "predev": "loclizr build --no-fail",
     "prebuild": "loclizr build",
     "pretypecheck": "loclizr build"

   Add this step to CI:

     # loclizr check compares the committed context record against this tree.
     # loclizr build would rewrite that record in the CI workspace and pass.
     - run: npx loclizr check
   ```

   `init` never overwrites a file that exists, and it prints the scripts rather than editing
   `package.json` for you. The config it writes is four lines:

   ```ts title="loclizr.config.ts"
   import { defineConfig } from 'loclizr'

   export default defineConfig({
     sourceLocale: 'en',
     catalogs: 'locales/{locale}.json',
     outDir: 'src/loclizr',
     severity: { 'ambiguous-source': 'error' },
   })
   ```

   The install comes first because that file imports `loclizr`. Run `build` before it and the
   config fails to load: `LZ1001 config-invalid`, exit 2.

   The `severity` line is the one decision `init` makes for you. `ambiguous-source` ships at
   `warn`; with no catalog yet, `init` writes it at `error`, because a hard gate costs nothing
   before the first string exists.

2. ### Write a catalog

   ```json title="locales/en.json"
   {
     "nav": {
       "home": "Home",
       "cart": "Cart"
     },
     "cart": {
       "greeting": "Hi {name}, your cart is ready",
       "items": "{count, plural, =0 {Your cart is empty} one {# item in your cart} other {# items in your cart}}"
     }
   }
   ```

   A catalog is nested JSON with ICU MessageFormat values; `init` seeds this one. The format is
   decided per file: `catalogFormat` defaults to `'auto'`, under which a file whose values carry
   `{{var}}` or whose keys carry `_one` and `_other` suffixes is read as i18next and converted to
   ICU in memory. That is why `init` writes no `catalogFormat` line: an imported i18next file can
   sit beside this one and both read correctly.

   ```json title="locales/en.meta.json"
   {
     "cart.items": {
       "description": "Badge under the cart icon on every page.",
       "placeholders": {
         "count": "Number of line items, not total quantity."
       }
     }
   }
   ```

   Descriptions live in a sidecar, so a translation management system never ships your notes to
   a translator as copy.

3. ### Build

   ```bash
   npx loclizr build
   ```

   ```txt frame="terminal" title="npx loclizr build"
   wrote src/loclizr (11 files) and locales/loclizr.context.json
   commit locales/loclizr.context.json; `loclizr check` compares it
   4 messages, 1 locale (source en), 0 errors, 0 warnings
   ```

   One pass wrote the generated tree, ran the whole rule set and wrote the context record:

   <FileTree>
   - locales
     - en.json
     - loclizr.context.json committed
   - loclizr.config.ts
   - src
     - loclizr
       - .gitignore self-ignoring
       - messages.js
       - messages.d.ts
       - messages
         - _formats.js
         - _formats.d.ts
         - _locale.js
         - _locale.d.ts
         - cart.js
         - cart.d.ts
         - nav.js
         - nav.d.ts
   </FileTree>

   The generated tree ignores itself through the `.gitignore` written inside it, so nothing in
   your root ignore file changes. The record is not ignored, because the record is the artifact
   that belongs in the pull request.

   ```ts title="src/loclizr/messages/cart.d.ts"
   // @generated by loclizr abi=1. Do not edit; run `loclizr build`.
   import type { MessageOptions } from 'loclizr'
   /** en: "Hi {name}, your cart is ready" */
   export declare function cart_greeting(args: { name: string | number }, opts?: MessageOptions): string
   /** en: "{count, plural, =0 {Your cart is empty} one {# item in your cart} other {# items in your cart}}" */
   export declare function cart_items(args: { count: number }, opts?: MessageOptions): string
   ```

   Declarations are printed as text, one module per top-level key segment.

4. ### Use the messages

   ```tsx title="src/Cart.tsx"
   import * as m from './loclizr/messages'

   export function Cart({ count }: { count: number }) {
     return <p>{m.cart_items({ count })}</p>
   }
   ```

   `m.cart_items({ count: '3' })` is a type error. The locale is read when the function is
   called, so a switch needs no reload, but a message call is not a subscription: the component
   re-renders when React re-renders it.

   - The example app keys its root on the locale, `<App key={useLocale()} />`, so every string
     below it is computed again on a switch.
   - A component that must keep its state across the switch passes the locale itself,
     `m.cart_items({ count }, { locale: useLocale() })`, and re-renders in place.

   Both patterns are in [Language switching](/guides/language-switching/).

   ```txt frame="terminal" title="npx loclizr build"
   wrote locales/loclizr.context.json
   commit locales/loclizr.context.json; `loclizr check` compares it
   4 messages, 1 locale (source en), 0 errors, 0 warnings
   ```

   ```json title="locales/loclizr.context.json" {3}
   "usage": [
     {
       "file": "src/Cart.tsx",
       "scope": "Cart"
     }
   ]
   ```

   Rebuilding now changes one thing. The record gains a usage entry for `cart.items`, the file
   and the enclosing function, and nothing else moves.

5. ### Add a locale

   Drop a `de.json` beside the source catalog and leave a key out:

   ```txt frame="terminal" title="npx loclizr build"
   error  LZ3001  missing-translation  locales/de.json  de  cart.items

     The de catalog has no value for this key, so this message renders en text.

     fix  add "cart.items" to locales/de.json

   warn  LZ5007  record-rewritten  locales/loclizr.context.json

     `locales/loclizr.context.json` was rewritten: the committed record's contract differs from the one these catalogs produce.

     fix  commit the rewritten record with the string change, so the context lands in the same pull request.

   wrote src/loclizr (5 files) and locales/loclizr.context.json
   4 messages, 2 locales (source en), 1 error, 1 warning
   fell back to source text: de 1
   ```

   The build names the key on the first run, with the fallback it applied, and the error still
   emitted: `messages/cart.js` now carries a `de` arm for every message, the missing one filled
   from English, and the exit code is 1. The warning is the record noticing that the locale list
   grew, a change to the contract the committed file describes.

   ```txt frame="terminal" title="npx loclizr build"
   wrote src/loclizr (1 file) and locales/loclizr.context.json
   commit locales/loclizr.context.json; `loclizr check` compares it
   4 messages, 2 locales (source en), 0 errors, 0 warnings
   ```

   Add the key and both go quiet.

6. ### Gate the build

   Put the step `init` printed into CI, and use `check` rather than `build` there. `check` does
   everything `build` does, writes nothing, and compares the tree on disk with what it would
   have written. Reword an English string and run it without rebuilding:

   ```txt frame="terminal" title="npx loclizr check"
   error  LZ5002  output-stale  src/loclizr/messages/cart.d.ts

     `src/loclizr/messages/cart.d.ts` differs from what this build would write.

     fix  the generated tree on disk is stale; run `loclizr build`.

   error  LZ5002  output-stale  src/loclizr/messages/cart.js

     `src/loclizr/messages/cart.js` differs from what this build would write.

     fix  the generated tree on disk is stale; run `loclizr build`.

   error  LZ5003  record-stale  locales/loclizr.context.json

     `locales/loclizr.context.json` no longer matches the catalogs: the contract this build derived differs from the committed record.

     fix  run `loclizr build` and commit the record with the string change.

   4 messages, 2 locales (source en), 3 errors, 0 warnings
   ```

   `build` in that same tree would rewrite the record, print `LZ5007` as a warning, and exit 0,
   exactly the outcome a CI workspace must not have. The scripts `init` printed put `build` in
   `prepare`, `predev`, `prebuild` and `pretypecheck`, so a fresh clone has a generated tree
   before anything imports it; `check` is the only command that belongs in the pipeline.

</Steps>

<Aside type="note">
There is no `--watch`. The dev loop is `loclizr build --no-fail` in `predev`, which reports every
diagnostic and exits 0 once output was written, so one untranslated key never stops `vite dev`.
The example app adds a twenty-line plugin in its own `vite.config.ts` that reruns the compiler when
a file under `locales/` changes; [How it works](/start/how-it-works/) shows it.
</Aside>
