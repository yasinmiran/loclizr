<Aside type="caution">
The package is not on npm yet, so `npm i loclizr` fails until the first release. Until then, build
the package from a clone and install the tarball it packs:

```bash
git clone <repo> && cd loclizr && pnpm install && pnpm build
pnpm --dir packages/loclizr pack
```

That writes `packages/loclizr/loclizr-0.0.0.tgz` inside the clone. Create the app beside the
clone, and wherever the steps below say `npm i loclizr`, run
`npm i ../loclizr/packages/loclizr/loclizr-0.0.0.tgz` instead. Every transcript on this page was
produced that way and pasted, not typed.
</Aside>

<Steps>

1. ### Create the app

   loclizr needs Node 20.19 or newer. The CLI loads its `.ts` config itself, so nothing else is
   required.

   ```bash
   npm create vite@latest my-shop -- --template react-ts
   cd my-shop
   npm i
   ```

   The template is the only part of this page that is Vite-specific. The generated messages are
   plain ESM and run under Node, a bundler or React Native alike.

2. ### Install, then initialise

   ```bash
   npm i loclizr
   npx loclizr init
   ```

   ```txt frame="terminal" title="npx loclizr init"
   wrote loclizr.config.ts
   wrote locales/en.json

   Install loclizr, which loclizr.config.ts and the generated code import:

     npm i loclizr

   Add these scripts to package.json:

     "predev": "loclizr build --no-fail",
     "prebuild": "loclizr build",
     "pretypecheck": "loclizr build"

   Add this step to CI, before any step that runs loclizr build:

     # loclizr check compares the committed context record against this tree.
     # loclizr build would rewrite that record in the CI workspace and pass.
     - run: npx loclizr check
   ```

   The note names a regular dependency, not a dev one, because the generated functions import
   the locale store from `loclizr` at run time: a Vite SPA bundles it either way, and a Node
   server needs it installed. The note prints whether or not the package is installed.

   `init` never overwrites a file that exists, and it prints the scripts rather than editing
   `package.json` for you. The config it writes has four options:

   ```ts title="loclizr.config.ts"
   import { defineConfig } from 'loclizr'

   export default defineConfig({
     sourceLocale: 'en',
     catalogs: 'locales/{locale}.json',
     outDir: 'src/loclizr',
     severity: { 'ambiguous-source': 'error' },
   })
   ```

   The install comes first because that file imports `loclizr`. Run `build` before it and the
   config fails to load: `LZ1001 config-invalid`, exit 2. Every diagnostic has a code like that,
   and [Checks](/reference/checks/) lists all fifty-six.

   The `severity` line is the one decision `init` makes for you. `ambiguous-source` fires when
   two keys share one source text and one of them has no description. It ships at `warn`; with
   no catalog yet, `init` writes it at `error`, because a hard gate costs nothing before the
   first string exists.

3. ### Add the scripts

   The template's `scripts` block with the three printed hooks added, plus a `typecheck` script
   to hang the third one on:

   ```json title="package.json"
   "scripts": {
     "predev": "loclizr build --no-fail",
     "dev": "vite",
     "prebuild": "loclizr build",
     "build": "tsc -b && vite build",
     "lint": "oxlint",
     "preview": "vite preview",
     "pretypecheck": "loclizr build",
     "typecheck": "tsc -b"
   }
   ```

   - `predev` runs before `npm run dev`, with `--no-fail` so one untranslated key never stops the
     dev server. `prebuild` runs before `npm run build` and takes the real exit code.
   - `typecheck` is `tsc -b` because the template's `tsconfig.json` is a list of project
     references with no files of its own; `tsc -p tsconfig.json` would check nothing.
   - There is no `prepare`. It would run on `npm ci`, so in CI it would rewrite the record before
     `check` compares it. The cost is editor squiggles under `./loclizr/messages` on a fresh
     clone until the first `npm run dev` or `npm run build`.

4. ### Write a catalog

   ```json title="locales/en.json"
   {
     "nav": {
       "home": "Home",
       "cart": "Cart"
     },
     "cart": {
       "greeting": "Hi {name}, your cart is ready",
       "items": "{count, plural, =0 {Your cart is empty} one {# item in your cart} other {# items in your cart}}"
     }
   }
   ```

   A catalog is nested JSON whose values are ICU MessageFormat, the syntax inside the strings:
   `{name}` is a placeholder, `{count, plural, ...}` picks a form by number, and `#` inside it is
   the number. `init` seeds this one; [Catalogs](/guides/catalogs/) has the rest of the syntax.

   The format is decided per file: `catalogFormat` defaults to `'auto'`, under which a file whose
   values carry `{{var}}` or whose keys carry `_one` and `_other` suffixes is read as i18next and
   converted to ICU in memory. That is why `init` writes no `catalogFormat` line: an imported
   i18next file can sit beside this one and both read correctly.

   Translator notes go in a sidecar, a second file beside the catalog. `init` does not write this
   one, and the build runs the same with or without it:

   ```json title="locales/en.meta.json"
   {
     "cart.items": {
       "description": "Badge under the cart icon on every page.",
       "placeholders": {
         "count": "Number of line items, not total quantity."
       }
     }
   }
   ```

   The notes live beside the catalog rather than inside it because a TMS (a translation
   management system, the web app translators work in, such as Crowdin, Lokalise or Phrase)
   imports your JSON and shows each string to a translator; a description written into `en.json`
   would ship as copy.

5. ### Build

   ```bash
   npx loclizr build
   ```

   ```txt frame="terminal" title="npx loclizr build"
   warn  LZ5004  scan-found-nothing

     The scan read 2 files and found no import of the generated messages.

     fix  check scan.include in loclizr.config.ts. A usage site is found through an import such as import * as m from './loclizr/messages'

   wrote src/loclizr (11 files) and locales/loclizr.context.json
   commit locales/loclizr.context.json; `loclizr check` compares it
   4 messages, 1 locale (source en), 0 errors, 1 warning
   ```

   One pass wrote the generated tree, ran the whole rule set and wrote the context record. The
   warning is right: the template's `App.tsx` and `main.tsx` import nothing from the tree yet.
   The next step adds the import, and the build after it is clean.

   <FileTree>
   - locales
     - en.json
     - en.meta.json
     - loclizr.context.json committed
   - loclizr.config.ts
   - src
     - loclizr
       - .gitignore self-ignoring
       - messages.js
       - messages.d.ts
       - messages
         - _formats.js
         - _formats.d.ts
         - _locale.js
         - _locale.d.ts
         - cart.js
         - cart.d.ts
         - nav.js
         - nav.d.ts
   </FileTree>

   The generated tree ignores itself through the `.gitignore` written inside it, so nothing in
   your root ignore file changes. The record is not ignored, because the record is the artifact
   that belongs in the pull request: per message, the source text, the argument types, the plural
   shape, where it is used and your description, for whoever translates next.
   [Context record](/reference/context-record/) has the schema.

   ```ts title="src/loclizr/messages/cart.d.ts"
   // @generated by loclizr abi=1. Do not edit; run `loclizr build`.
   import type { MessageOptions } from 'loclizr'
   /** en: "Hi {name}, your cart is ready" */
   export declare function cart_greeting(args: { name: string | number }, opts?: MessageOptions): string
   /** en: "{count, plural, =0 {Your cart is empty} one {# item in your cart} other {# items in your cart}}" */
   export declare function cart_items(args: { count: number }, opts?: MessageOptions): string
   ```

   Declarations are printed as text, one module per top-level key segment. `abi=1` in the header
   is the version of the four helpers the generated code imports from `loclizr`.

6. ### Use the messages

   ```tsx title="src/Cart.tsx"
   import * as m from './loclizr/messages'

   export function Cart({ count }: { count: number }) {
     return <p>{m.cart_items({ count })}</p>
   }
   ```

   <Aside type="tip">
   If `./loclizr/messages` is red in the editor, the tree has not been generated yet: run
   `npx loclizr build`. `predev` and `prebuild` from the scripts step run it for you.
   </Aside>

   Under Vite the import is extensionless. Under Node's own resolver write
   `./loclizr/messages.js`, and `package.json` needs `"type": "module"`, which the Vite template
   already has.

   The file sits under `src/` because the usage scan, which reads your source to note where each
   message is called, covers `src/**/*.{ts,tsx,js,jsx,mts,mjs}` by default (`scan.include` in the
   config). Rebuild:

   ```txt frame="terminal" title="npx loclizr build"
   wrote locales/loclizr.context.json
   commit locales/loclizr.context.json; `loclizr check` compares it
   4 messages, 1 locale (source en), 0 errors, 0 warnings
   ```

   ```json title="locales/loclizr.context.json" {3}
   "usage": [
     {
       "file": "src/Cart.tsx",
       "scope": "Cart"
     }
   ]
   ```

   Rebuilding changes one thing. The record gains a usage entry for `cart.items`, the file and
   the enclosing function, the scan warning is gone, and nothing else moves.

   Change the call to `m.cart_items({ count: String(count) })` and the type the declaration
   printed holds:

   ```txt frame="terminal" title="npm run typecheck"
   > my-shop@0.0.0 pretypecheck
   > loclizr build

   4 messages, 1 locale (source en), 0 errors, 0 warnings

   > my-shop@0.0.0 typecheck
   > tsc -b

   src/Cart.tsx(4,29): error TS2322: Type 'string' is not assignable to type 'number'.
   ```

   A literal `{ count: '3' }` fails the same way, with a second line from the template's
   `noUnusedLocals` about the prop it no longer reads. Put the call back.

7. ### Add a locale

   Drop a `de.json` beside the source catalog and leave `cart.items` out:

   ```json title="locales/de.json"
   {
     "nav": {
       "home": "Startseite",
       "cart": "Warenkorb"
     },
     "cart": {
       "greeting": "Hallo {name}, dein Warenkorb ist bereit"
     }
   }
   ```

   ```txt frame="terminal" title="npx loclizr build"
   error  LZ3001  missing-translation  locales/de.json  de  cart.items

     The de catalog has no value for this key, so this message renders en text.

     fix  add "cart.items" to locales/de.json

   warn  LZ5007  record-rewritten  locales/loclizr.context.json

     `locales/loclizr.context.json` was rewritten: the committed record's contract differs from the one these catalogs produce.

     fix  commit the rewritten record with the string change, so the context lands in the same pull request.

   wrote src/loclizr (5 files) and locales/loclizr.context.json
   4 messages, 2 locales (source en), 1 error, 1 warning
   fell back to source text: de 1
   ```

   The build names the key on the first run, and the output still exists: `messages/cart.js` now
   carries a `de` arm for `cart_greeting`, while `cart_items` keeps its single `default` arm and
   renders English, and the exit code is 1. A locale with no value for a key renders the source
   locale's text; that is the fallback the summary line counts.

   The warning is the record noticing that the locale list grew, a change to the contract the
   committed file describes: keys, source text, argument types, plural shapes. Committed here
   means the file the previous build left on disk; in a repository it is the one you checked in.
   [What the gate compares](/guides/continuous-integration/#what-the-gate-compares) lists it.

   Add `cart.items` to `de.json` and both go quiet:

   ```json title="locales/de.json" {3}
   "cart": {
     "greeting": "Hallo {name}, dein Warenkorb ist bereit",
     "items": "{count, plural, =0 {Dein Warenkorb ist leer} one {# Artikel in deinem Warenkorb} other {# Artikel in deinem Warenkorb}}"
   }
   ```

   ```txt frame="terminal" title="npx loclizr build"
   wrote src/loclizr (1 file) and locales/loclizr.context.json
   commit locales/loclizr.context.json; `loclizr check` compares it
   4 messages, 2 locales (source en), 0 errors, 0 warnings
   ```

8. ### Switch the language

   ```tsx title="src/Switcher.tsx"
   import { useLocale } from 'loclizr/react'
   import * as m from './loclizr/messages'

   export function Switcher() {
     const locale = useLocale()
     return (
       <div>
         {m.locales.map((tag) => (
           <button key={tag} type="button" aria-pressed={tag === locale} onClick={() => m.setLocale(tag)}>
             {tag}
           </button>
         ))}
       </div>
     )
   }
   ```

   ```tsx title="src/App.tsx"
   import * as m from './loclizr/messages'
   import { Cart } from './Cart'
   import { Switcher } from './Switcher'

   function App() {
     return (
       <>
         <Switcher />
         <h1>{m.cart_greeting({ name: 'Ada' })}</h1>
         <Cart count={3} />
       </>
     )
   }

   export default App
   ```

   ```tsx title="src/main.tsx" {3,7-9,13}
   import { StrictMode } from 'react'
   import { createRoot } from 'react-dom/client'
   import { useLocale } from 'loclizr/react'
   import './index.css'
   import App from './App.tsx'

   function Root() {
     return <App key={useLocale()} />
   }

   createRoot(document.getElementById('root')!).render(
     <StrictMode>
       <Root />
     </StrictMode>,
   )
   ```

   A message call reads the locale when it is called, so nothing subscribes on its own. The `key`
   makes React call every message under `App` again on a switch.

   `npm run dev`, and the page shows two buttons, `de` and `en`, in the order of `m.locales`.
   Click `de`: the heading reads `Hallo Ada, dein Warenkorb ist bereit`, the paragraph
   `3 Artikel in deinem Warenkorb`, and a reload keeps German, since `setLocale` wrote a cookie.
   [Language switching](/guides/language-switching/) has the pattern that keeps component state
   across the switch.

9. ### Gate the build

   Put the step `init` printed into CI, and use `check` rather than `build` there. `check` does
   everything `build` does, writes nothing, and compares the tree on disk with what it would
   have written. Reword `cart.greeting` in `en.json` and run `check` without rebuilding:

   ```txt frame="terminal" title="npx loclizr check"
   error  LZ5002  output-stale  src/loclizr/messages/cart.d.ts

     `src/loclizr/messages/cart.d.ts` differs from what this build would write.

     fix  the generated tree on disk is stale; run `loclizr build`.

   error  LZ5002  output-stale  src/loclizr/messages/cart.js

     `src/loclizr/messages/cart.js` differs from what this build would write.

     fix  the generated tree on disk is stale; run `loclizr build`.

   error  LZ5003  record-stale  locales/loclizr.context.json

     `locales/loclizr.context.json` no longer matches the catalogs: the contract this build derived differs from the committed record.

     fix  run `loclizr build` and commit the record with the string change.

   4 messages, 2 locales (source en), 3 errors, 0 warnings
   ```

   `build` in that same tree would rewrite the record, print `LZ5007` as a warning, and exit 0,
   exactly the outcome a CI workspace must not have. `check` is the only loclizr command that
   belongs in the pipeline, and it has to run before anything that runs `build`:

   ```yaml title=".github/workflows/ci.yml"
   - run: npm ci
   - run: npx loclizr check
   ```

   None of the three scripts runs on install, so a plain `npm ci` runs nothing of loclizr's and
   the record `check` compares is the committed one. A `prepare` hook of your own that ran
   `loclizr build` would reintroduce the problem, since `prepare` runs on `npm ci`.
   [Continuous integration](/guides/continuous-integration/) has the whole workflow.

</Steps>

<Aside type="note">
There is no `--watch`. The dev loop is `loclizr build --no-fail` in `predev`, which reports every
diagnostic and exits 0 once output was written, so one untranslated key never stops `vite dev`.
The example app adds a small plugin in its own `vite.config.ts` that reruns the compiler when a
file under `locales/` changes; [How it works](/start/how-it-works/) shows it.
</Aside>
