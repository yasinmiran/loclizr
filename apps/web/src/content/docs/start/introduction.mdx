```ts title="src/Cart.tsx"
import * as m from './loclizr/messages'

m.cart_greeting({ name: 'Ada' })   // "Hi Ada, your cart is ready"
m.cart_items({ count: 3 })         // "3 items in your cart"
m.cart_items({ count: '3' })       // type error: count is a number
```

loclizr is a command line compiler. `loclizr build` reads the JSON catalogs you keep under
`locales/` and writes typed ESM message functions into your source tree. Your app calls them like
any other function.

- No bundler plugin, no AST pass, nothing rewrites application code: no transform ordering for a
  framework's next compiler release to break.
- One output runs in a Vite SPA, a server render, React Native and plain Node.
- ICU MessageFormat is parsed at build time; the browser ships no parser.
- The locale is read at call time, so switching language needs no reload.

<Aside type="caution">
Nothing is published to npm yet. v0.1 is in development, and these pages describe the contract it
is being built against.
</Aside>

## What one build produces

### Message modules

One module per top-level key segment, each message a function whose first parameter is exactly
its ICU argument set. A renamed placeholder, or a plural argument handed a string, fails your
typecheck at the call site rather than rendering `undefined` to somebody.

### Diagnostics, from the same pass

Checking is part of `build`, on from the first run, and an error exits 1. Missing and blank
translations, ICU syntax errors, arguments that differ between two locales, plural categories a
locale can never select, keys that differ only by a homoglyph.

Fifty-six rules, each with a stable code; all but three re-level to `off`, `warn` or `error` from
one line of config. Other tools check catalogs too, usually as a step you remember to wire up,
where here it is the default.

### A context record

Written to `locales/loclizr.context.json`, meant to be committed. Per message: the canonical
source text and a hash of it, argument names and types, the plural or select shape, the file and
enclosing function where the message is used, per-locale translation status, and your description
if you wrote one.

No timestamps and no line numbers, so it moves when the contract moves, in the same pull request
as the string edit. Whoever translates next reads it: a person, a model or a TMS.

## Who it is for

A new app is the easy case: catalogs from the first commit, a hard gate from the first commit,
nothing to unlearn. The more common case is an app whose strings are still English literals
sitting in JSX, where the thing you are replacing is not another library.

Already on i18next? Point `catalogs` at the files you have. Nothing is written back, so i18next
keeps serving the app while you read the diagnostics. The format is decided per file, not per
project: `{{name}}` interpolation or `_one` and `_other` keys mark a file as i18next, the
interpolation becomes an ICU argument and the suffixed keys fold into one plural, all in memory,
beside any ICU-native file.

## What it deliberately does not do

| Not in v0.1 | What that means |
| --- | --- |
| Per-locale delivery | Every declared locale of every used message is inlined into that function; bundle size grows with locale count. Paraglide is built around shipping one locale's strings per request. |
| Extraction, codemod | Nothing reads your components looking for strings or rewrites one. Catalogs are authored or imported; the retrofit work is yours. |
| A second framework | React with Vite is the tested example; the message layer itself is framework free. Server rendering covers Web Fetch handlers through `withLocale`, and plain header strings (Express, Fastify) through `localeFromHeaders` plus `runWithLocale`. Next.js is not a first-class target; next-intl is built for that stack. |
| Runtime catalogs | A translation fix is a commit and a deploy. A TMS that opens pull requests is fine; a dashboard where somebody fixes a production typo at 4pm is not what this is. |
| `--watch` | The dev loop is `loclizr build --no-fail` in `predev`, plus the inline Vite plugin the example ships in its own `vite.config.ts` for catalog edits to reach the running app. |
| A track record | Day zero: no published release, no promise about stability. |
