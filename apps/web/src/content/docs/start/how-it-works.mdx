## Catalog in

`loclizr build` globs `locales/{locale}.json`, flattens each file to dotted keys and classifies it
on its own. No catalog is ever written back.

| File | Read as |
| --- | --- |
| Values carry `{{var}}`, or keys carry a CLDR plural suffix | i18next, rewritten to ICU in memory |
| Anything else | ICU, the native format |

The example app's `de-AT.json` is the i18next case, beside two ICU files, with nothing in the
config saying so.

The source locale's sidecar, `en.meta.json`, is read in the same pass. Descriptions and
placeholder notes live there, out of the catalog, so a translation tool never ships them as copy.

## One representation

Every value is parsed with `@formatjs/icu-messageformat-parser` exactly once and lowered to a
small tree: text nodes, arguments with inferred types, plural and select branches, markup tags.
Each locale keeps its own lowered body. The fallback chain then runs, `de-AT` through `de` to
`en`, and stamps one origin per locale per message: translated, inherited, or fell back to source.

Everything downstream reads that tree, never the JSON. A rule compares argument sets across
locales without re-parsing, and a diagnostic cannot disagree with the emitted code, since both
came from one structure.

## Three outputs

### Typed functions

One module per top-level key segment under `src/loclizr/messages/`, plain ESM with a hand-printed
`.d.ts` beside it. Each message is a function: first parameter exactly its ICU argument set, body
a `switch` over the declared locales with the source locale under `default`. The generated
`.gitignore` ignores the whole directory, and the header on every file lets the next build prune
what it wrote and nothing else.

### Diagnostics

The rule set runs in the same pass over the same tree. A fatal error, invalid config or an
identifier collision say, blocks emission. A non-fatal error still emits: twelve missing German
strings write `messages/cart.js` with those twelve filled from the chain, print twelve `LZ3001`
lines and exit 1, since emitting nothing would bury the real problem under missing-module errors
from your typecheck.

### The context record

`locales/loclizr.context.json` carries, per message, the canonical source and a hash of it,
argument names and types, the plural or select shape, your description, per-locale status, and
the file and enclosing scope the message is called from.

It is a pure function of the tree: no timestamps, no tool version, no line numbers, never its own
previous value. `check` compares the committed copy against what it would write, with `usage` and
`translations` projected out, so a moved component or a translator's batch cannot fail the gate
but an edited string does.

## Runtime

The generated code imports four helpers from `loclizr`: a locale resolver and thin wrappers over
`Intl.PluralRules`, `Intl.NumberFormat` and `Intl.DateTimeFormat`, formatters cached by options
identity. Nothing else. No ICU parser reaches the browser; parsing finished at build time, and what
shipped is a function with a `switch` in it.

### What runs where

| Where | What loads | Size, gzipped and unminified |
| --- | --- | --- |
| Browser | The generated tree and the `loclizr` entry: the locale store, a cookie reader, the locale resolver and the three `Intl` wrappers. No dependencies; the entry imports only its own store chunk. | The example's tree, 26 messages in 3 locales across 10 modules: 8.8 kB raw, 1.9 kB gzipped. The store as shipped in `dist`: 6.1 kB raw, 2.1 kB gzipped. |
| Server | Adds `loclizr/server`, which imports `node:async_hooks` for `AsyncLocalStorage`. | |
| Build and CI | `loclizr/compiler` and the CLI, with the package's four production dependencies: `@formatjs/icu-messageformat-parser`, `jiti`, `picocolors`, `tinyglobby`. | |

[Security](/project/security/) takes that surface further.

### Resolving the locale

`getLocale()` reads, in order:

1. the server request scope, if one is active
2. the tag `setLocale` stored
3. on the client, the cookie, then `<html lang>`
4. the source locale

Passing `{ locale }` as the second argument overrides all of that for one call. On the server,
`runWithLocale` scopes the value through `AsyncLocalStorage`, so no mutable process-wide locale
exists for two requests to fight over.

<Aside type="note">
A message call reads the store and returns a string; it does not subscribe. That is why the
example keys its root on `useLocale()`, and why the per-call `{ locale }` form exists for a
component that must keep its state across a switch.
</Aside>

## Why no bundler plugin, and what it costs

Nothing here transforms your source. The app imports `./loclizr/messages` like any other module,
so there is no AST pass to order against a framework compiler, and the same output runs in a Vite
SPA, a server render, React Native and plain Node.

The price is a build step and generated files in the tree.

- `src/loclizr/` has to exist before anything imports it; the `prepare`, `predev`, `prebuild` and
  `pretypecheck` scripts are for that.
- It is gitignored by default, so a fresh clone runs `build` before anything else.
- No `--watch`. The loop is `loclizr build --no-fail` in `predev`, which exits 0 once output was
  written whatever it found, so one untranslated key never stops `vite dev`.

### The example's Vite plugin

```ts title="vite.config.ts" {9,18}
import react from '@vitejs/plugin-react'
import { defineConfig, normalizePath, type Plugin } from 'vite'

function loclizrCatalogs(): Plugin {
  return {
    name: 'loclizr-catalogs',
    configureServer(server) {
      const root = server.config.root
      const catalogs = normalizePath(`${root}/locales`)
      const record = `${catalogs}/loclizr.context.json`
      let pending = Promise.resolve()
      const rebuild = (changed: string): void => {
        const file = normalizePath(changed)
        if (!file.startsWith(`${catalogs}/`) || file === record) return
        pending = pending
          .then(async () => {
            const { build } = await import('loclizr/compiler')
            const { summary } = await build({ cwd: root, failOnError: false })
            const counts = `${summary.messages} messages, ${summary.errors} errors, ${summary.warnings} warnings`
            server.config.logger.info(`loclizr rebuilt ${file.slice(root.length + 1)}: ${counts}`)
          })
          .catch((error: unknown) => {
            server.config.logger.error(`loclizr rebuild failed: ${String(error)}`)
          })
      }
      server.watcher.add(catalogs)
      server.watcher.on('add', rebuild)
      server.watcher.on('change', rebuild)
      server.watcher.on('unlink', rebuild)
    },
  }
}

export default defineConfig({
  plugins: [react(), loclizrCatalogs()],
})
```

For a catalog edit to land in the running app, the example ships this inside its own
`vite.config.ts`: `configureServer` adds `locales/` to the dev server's watcher and calls `build`
from `loclizr/compiler` when a file under it changes. The compiler rewrites `src/loclizr/**`,
already in Vite's module graph, and HMR does the rest.

Two lines change when you copy it, both marked: the watched directory, when `catalogs` in your
config points somewhere other than `locales/`, and `failOnError: false`, which keeps the dev
server up through an untranslated key the way `--no-fail` does in `predev`. Without a plugin, one
process beside the dev server does the same job: `nodemon -w locales -x 'loclizr build --no-fail'`.

It reruns the compiler and touches no app source, so the narrow promise holds: no plugin is
required, nothing rewrites your code, and the lines that make the loop tight are yours rather than
a package you depend on.
