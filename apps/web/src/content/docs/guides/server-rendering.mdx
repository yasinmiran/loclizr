```ts
runWithLocale<T>(locale: string, fn: () => T): T
withLocale(handler, options: NegotiateOptions): (request: Request, ...rest) => Promise<Response>
localeFromRequest(request: Request, options: NegotiateOptions): string
localeFromHeaders(headers: { cookie?: string; acceptLanguage?: string }, options: NegotiateOptions): string
negotiate(accepted: readonly string[], options: NegotiateOptions): string
```

No mutable global locale on the server: `loclizr/server` installs an `AsyncLocalStorage` scope per
request, every message call inside it resolves to that request's locale, and concurrent requests
cannot see each other. The four negotiating functions take the locale list as `NegotiateOptions`,
`{ locales, sourceLocale, cookie? }`; the generated barrel exports the first two. `runWithLocale`
takes a locale you already chose.

## Scope, stated first

| Host | v0.1 |
| --- | --- |
| Web Fetch handlers: Vite SSR, Hono, TanStack Start, Bun, Deno, Workers with `nodejs_als` | `withLocale` |
| Express, Fastify, anything with `req.headers` instead of a `Request` | `localeFromHeaders`, then `runWithLocale` around the render |
| Next.js, App Router or Pages Router middleware | not first-class: no test, no example, no promise |

Middleware runs in a different runtime and cannot wrap a render; the App Router entry is an open
question.

## A Fetch handler

<figure class="diagram">

![A request path: the page sends GET /cart with its cookie and Accept-Language, withLocale negotiates the locale and opens a runWithLocale scope, your handler renders through the generated message functions, and the response carries Content-Language. In the browser the loclizr store reads the cookie first, so hydration lands on the same locale.](../../../assets/diagrams/server-request.svg)

```ts title="src/server.ts"
import { withLocale } from 'loclizr/server'
import * as m from './loclizr/messages.js'

const options = { locales: m.locales, sourceLocale: m.sourceLocale }

export const handler = withLocale(
  () => new Response(`<html lang="${m.getLocale()}"><h1>${m.cart_greeting({ name: 'Ada' })}</h1></html>`),
  options,
)
```

<Steps>

1. `withLocale` negotiates from the request.
2. The handler runs inside the scope.
3. Two headers go on the response.

</Steps>

<Aside type="note">
The generated tree is ESM, so wherever Node runs it `package.json` needs `"type": "module"`.
Under Node's own resolver, or `moduleResolution: nodenext`, import `./loclizr/messages.js` with
the extension, as the snippet does; under a bundler the extension is optional. The example app's
`package.json` has the field, which is why every snippet on this page ran as written.
</Aside>

Three requests against the example catalogs:

```text
cookie wins
  Content-Language: de-AT
  Vary: Accept-Language
  body: <html lang="de-AT"><h1>Servus Ada, dein Einkaufswagerl ist fertig</h1></html>
accept-language when no cookie
  Content-Language: de
  Vary: Accept-Language
  body: <html lang="de"><h1>Hallo Ada, dein Warenkorb ist fertig</h1></html>
nothing matches
  Content-Language: en
  Vary: Accept-Language
  body: <html lang="en"><h1>Hi Ada, your cart is ready</h1></html>
```

| Request carried | Result |
| --- | --- |
| `cookie: locale=de-AT` and `accept-language: en` | the cookie won |
| `accept-language: de-CH,de;q=0.9,en;q=0.8`, no cookie | `de-CH` truncated to the declared `de` |
| `fr` | the source locale |

<Aside type="caution">
`Vary: Accept-Language` is set, and most CDNs ignore `Vary` outside `Accept-Encoding`. A response
whose locale came from the cookie must stay out of shared caches: `Cache-Control: private`, or
key the CDN cache on the locale cookie.
</Aside>

## Cookie first, then Accept-Language

`localeFromHeaders` is the primitive. `localeFromRequest` reads the two headers off a `Request`
and passes them through, so the order has one implementation:

<Steps>

1. The configured cookie.
2. `Accept-Language`, through `negotiate`: RFC 4647 lookup by subtag truncation, ranked by
   quality, with no dependency.
3. The source locale.

</Steps>

```ts title="server/app.ts"
import { localeFromHeaders, runWithLocale } from 'loclizr/server'
import * as m from '../src/loclizr/messages.js'

const options = { locales: m.locales, sourceLocale: m.sourceLocale }

app.get('/cart', (req, res) => {
  const locale = localeFromHeaders(
    { cookie: req.headers.cookie, acceptLanguage: req.headers['accept-language'] },
    options,
  )
  res.set('Content-Language', locale)
  res.send(runWithLocale(locale, () => render()))
})
```

Express and Fastify never hold a `Request`, so they call the primitive. `runWithLocale`, which
`withLocale` uses underneath, installs the scope on first call and runs `fn` inside it; no
per-request state lives outside the `AsyncLocalStorage`.

## html lang and Content-Language

The client reads the cookie, then `<html lang>`, nothing else. A visitor with no cookie and
`Accept-Language: de` gets German from the server and hydrates from whatever `lang` the markup
carries.

<Aside type="caution">
Hardcode `<html lang="en">` and the page renders German and hydrates English; nothing in the
library can see that from the server. Render `lang` from the negotiated locale, the value
`withLocale` put in `Content-Language`.
</Aside>

Outside production, `useLocale` checks `document.documentElement.lang` against the resolved locale
on the client and warns once when they disagree, naming that header.

## Outside a request

```text
loclizr: getLocale() ran outside a request scope, so it returned the source locale. Wrap the render in runWithLocale().
```

Inside a scope `setLocale` throws; pass `{ locale }` per call. Outside any scope a message call
quietly returns source-locale text, and `getLocale()` returns the source locale with that warning,
once per process outside production.

Warning rather than throwing is deliberate. Static prerender, background jobs, scripts and error
boundaries run with no request in hand; a 500 where source text would have degraded gracefully is
the wrong trade. Wrap them in `runWithLocale` to render a specific language.

## Dates on the server

```ts title="loclizr.config.ts"
export default defineConfig({
  formats: { timeZone: 'UTC' },
  severity: { 'date-without-timezone': 'error' },
})
```

A date formatted with no time zone resolves the server's default zone during render and the
viewer's on the client: one instant, two different days across the hydration boundary.
`LZ3011 date-without-timezone` catches every date and time style with no zone. It ships `off`,
since a browser SPA wants the viewer's own zone; turn it on wherever a server renders dates, and
set `formats.timeZone`, which is merged into every date and time style.
