import { Aside, Steps } from '@astrojs/starlight/components'

```ts title="loclizr.config.ts"
import { defineConfig } from 'loclizr'

export default defineConfig({
  catalogs: 'public/locales/{locale}/{ns}.json',
  sourceLocale: 'en',
})
```

Point `catalogs` at the files you already have and run `loclizr build`. Nothing is written back,
so i18next keeps serving the app while you read the diagnostics and the generated functions. The
default pattern is `locales/{locale}.json`; a split layout uses the `{ns}` token, and every key
from `common.json` is prefixed with `common.`.

Converts with zero edits:

- a clean JSON v4 catalog, one file per locale or the `{ns}` layout
- `{{name}}` placeholders, and `{{- name}}`: the unescape prefix has no job here, since nothing
  loclizr renders is HTML-escaped
- `_one` and `_other` plural suffixes, and `_zero`

Needs a catalog rewrite before the message is right. Every message function still exists, so the
page never goes blank while you fix them:

- `$t()` nesting and `{{x, fmt}}` inline formatters: `LZ1012` and `LZ1013` at `error`, the
  message rendering the literal text or the raw value
- `{{a.b}}` (nested access), or any placeholder name ICU cannot read: `LZ1013` at `error`, the
  placeholder kept as the literal characters and the hint naming the flat name to write
- context suffixes (`friend_male`): `LZ1017` at `warn`, every suffix emitted as its own message
- a JSON v3 `X` and `X_plural` pair: `LZ1014` at `warn`, both emitted as ordinary keys
- `<b>` and `<a>` left in values by `Trans`: `LZ1016` at `warn`, rendered as the characters
  until `i18nextMarkup: 'tags'`; under `'tags'`, a value holding a tag the parser rejects, such
  as a numbered `<1>`, stays text as a whole under the same rule code

Each is shown below with the diagnostic it prints.

## What auto detection does

The format is decided per file, after flattening and before any conversion.

| File | Read as |
| --- | --- |
| Any value contains `{{`, or any key carries a CLDR plural suffix that would fold | i18next |
| Otherwise | ICU |

There is no hybrid. In a file read as i18next, single-brace ICU syntax is literal text; in a file
read as ICU, `{{name}}` is a brace around an argument, as the ICU grammar says. The decision is
per file, not per value, so a translator's stray `{{` never flips the meaning of one string on
its own.

`catalogFormat: 'icu'` or `'i18next'` pins every file and skips the classification. The example
app runs with the default, which is how its ICU `de.json` and its i18next-form `de-AT.json` sit
side by side.

## What converts

| i18next | ICU | Notes |
| --- | --- | --- |
| `{{name}}` | `{name}` | Whitespace inside the braces trimmed; typed `string \| number`. |
| `{{- name}}` | `{name}` | The unescape prefix is dropped with no diagnostic. loclizr never HTML-escapes an argument, so the two spellings are one message. |
| `{{count}}` | `{count}` | Stays a plain argument: never rewritten to `#`, never passed through `Intl.NumberFormat`, since i18next printed it unformatted and `1000 items` becoming `1,000 items` on import day would be a silent change. As a folded plural's selector it narrows to `number`. |
| `items_one`, `items_other` | `items`, one ICU plural | Selector always `count`; branches ordered `=0, zero, one, two, few, many, other`. |
| `X_ordinal_one` | `selectordinal` | |
| `items_zero` | `=0` or `zero`, by locale | The compiler knows the locale. German never selects `zero`, so the exact branch `=0`; Latvian selects it for 10, 20 and 11 through 19, so the keyword branch stays. |

Same three keys in both files, two different arms. The Latvian arm names `'lv'` in its
`$plural1` call because the category follows the language of the body, not the visitor's locale;
the German arm needs no call, since its `one` and `other` bodies are the same text:

```js title="src/loclizr/messages/_root.js"
case 'de':
  if (n0 === 0) return `Dein Warenkorb ist leer`
  return `${args.count} Artikel in deinem Warenkorb`
case 'lv':
  switch ($plural1('lv', n0, false)) {
    case 'zero':
      return `Jūsu grozs ir tukšs`
    case 'one':
      return `${args.count} prece jūsu grozā`
    default:
      return `${args.count} preces jūsu grozā`
  }
```

A suffixed key with no `_other` sibling stays an ordinary key and warns:

```text
warn  LZ1014  plural-suffix-orphan  locales/en.json:9:19  en  cart.empty_one

  "cart.empty_one" carries a plural suffix with no "cart.empty_other" sibling, so it stays an ordinary key that i18next would never have selected either.

  fix  add cart.empty_other to fold the group, or rename the key if "_one" was never a plural.
```

So does the JSON v3 pair, a bare `cart.item` beside `cart.item_plural`:

```text
warn  LZ1014  plural-suffix-orphan  locales/en.json:5:21  en  cart.item_plural

  "cart.item_plural" is the i18next JSON v3 plural of "cart.item". Both stay ordinary keys, each rendering one grammatical number.

  fix  run i18next's JSON v3 to v4 converter over this catalog, so cart.item_one and cart.item_other fold into one plural message.
```

The build is green with that warning, and `m.cart_item({ count: 5 })` renders `5 item` in every
locale until the pair is folded by hand or by i18next's converter. Nothing selects the plural any
more, so a warning is all the compiler can say.

## Detected, not converted

Context suffixes are the one i18next feature that survives import as the wrong thing: `friend`,
`friend_male` and `friend_female` all become message functions and nothing selects between them
any more. The compiler will not guess the rewrite, so it prints it:

```text
warn  LZ1017  i18next-context-detected  locales/en.json:11:14  en  friend

  "friend" carries 2 context suffixes. i18next selected these with t('friend', { context }), and after import nothing selects them.

    friend_male      locales/en.json:12:19     selected by nothing after import
    friend_female    locales/en.json:13:21     selected by nothing after import

  fix  convert this file to ICU first, then replace them with one message:
    "friend": "{context, select, male {...} female {...} other {...}}"
```

<Aside type="caution">
"Convert this file to ICU first" is load bearing. Pasting that select into a file that still
contains `{{` puts ICU syntax into a file read as i18next, and the run renders as literal text.
</Aside>

## What does not convert

| Written | Rule | Why |
| --- | --- | --- |
| `$t(nav.home)` nesting | `LZ1012`, error | No ICU equivalent. |
| `{{amount, currency}}` inline formatter | `LZ1013`, error | No place in ICU to carry the format. |
| `{{user.name}}` nested access | `LZ1013`, error | A dot is not an ICU argument name. The characters stay literal text, the function exists, and the hint names the flat name to write. |
| An array value | `LZ1010 catalog-shape-invalid` | |
| ICU syntax in an i18next file | `LZ1020`, warn | The one mistake auto detection could otherwise make invisible. |

A four-key catalog, `Hi {{name}}, your cart is ready`, `Welcome back, {{- name}}`,
`Logged in as {{user.name}}` and a plain `nav.home`, builds as four messages:

```text
error  LZ1013  i18next-format-unsupported  locales/en.json:5:16  en  cart.nested

  The placeholder {{user.name}} names "user.name", which ICU cannot read as an argument. It renders as literal text.

  fix  give the argument one plain name: write {{userName}} here and pass userName at the call site.

wrote src/loclizr (11 files) and locales/loclizr.context.json
commit locales/loclizr.context.json; `loclizr check` compares it
4 messages, 1 locale (source en), 1 error, 0 warnings
```

```ts title="src/loclizr/messages/cart.d.ts"
// @generated by loclizr abi=1. Do not edit; run `loclizr build`.
import type { EmptyArgs, MessageOptions } from 'loclizr'
/** en: "Hi {name}, your cart is ready" */
export declare function cart_greeting(args: { name: string | number }, opts?: MessageOptions): string
/** en: "Logged in as '{{'user.name'}}'" */
export declare function cart_nested(args?: EmptyArgs, opts?: MessageOptions): string
/** en: "Welcome back, {name}" */
export declare function cart_raw(args: { name: string | number }, opts?: MessageOptions): string
```

`cart_raw` takes `name` exactly as `cart_greeting` does. `cart_nested` takes nothing:
`m.cart_nested()` renders `Logged in as {{user.name}}`, the text i18next printed for a missing
interpolation value, and its doc comment carries those braces quoted, as canonical ICU writes
literal text. The build exits `1` until the catalog says `{{userName}}` and the call site passes
`userName`.

The `LZ1012` and formatter `LZ1013` errors print the same way, the message rendering the
literal text or the raw value:

```text
error  LZ1012  i18next-nesting-unsupported  locales/en.json:8:16  en  cart.footer

  This value nests another key with $t(), which ICU cannot express, so the call renders as literal text.

  fix  inline the nested text here, or split the sentence into two messages.

error  LZ1013  i18next-format-unsupported  locales/en.json:7:15  en  cart.total

  The placeholder {{amount, currency}} carries an i18next formatter, which has no ICU equivalent. It renders as the raw value.

  fix  name the style in formats.number or formats.dateTime, convert this file to ICU, and write {amount, number, yourStyle}.
```

```text
warn  LZ1020  icu-in-i18next-file  locales/en.json:15:14  en  status

  "{state, select" is ICU argument syntax, and this file is read as i18next, so the whole run renders as literal text.

  fix  this file classified as i18next on "Hi {{name}}, your cart is ready". Convert the file to ICU, or pin catalogFormat if the literal text is what you meant.
```

## HTML in values

i18next catalogs are full of `<b>` and `<a>` because `Trans` put them there.

| `i18nextMarkup` | Effect |
| --- | --- |
| `'literal'`, the default | Tag-shaped text is escaped and rendered as the characters, what i18next itself rendered. Each such value raises `LZ1016 i18next-markup-literal` once so the choice is visible. `Read our <b>terms</b> before you continue.` stays a plain `string`. |
| `'tags'` | The same value lowers to a markup argument: `LZ1016` goes quiet for it, `b` becomes a required handler, and the return type changes at every call site, which is why it is a whole-catalog setting and not the default. |

```ts title="src/loclizr/messages/_root.d.ts"
/** en: "Read our <b>terms</b> before you continue." */
export declare function terms<T>(
  args: { b: (chunks: readonly (string | T)[]) => T },
  opts?: MessageOptions,
): readonly (string | T)[]
```

A tag the parser rejects never lowers: a numbered `<1>` from `Trans`, a tag with attributes, an
unclosed or mismatched tag, or a name cut by a placeholder. Under `'tags'` such a value is
escaped to text as a whole and raises `LZ1016` with a different message, so its return type stays
`string` and one stray tag never changes a signature. The same two values, `terms` above and
`"accept": "I accept the <1>terms of service</1>"`, under each mode:

```text title="i18nextMarkup: 'literal'"
warn  LZ1016  i18next-markup-literal  locales/en.json:2:13  en  terms

  Tag-shaped text in this value was escaped to literal text, which is what i18next itself rendered.

  fix  set i18nextMarkup: 'tags' to lower these tags to markup arguments instead.
```

```text title="i18nextMarkup: 'tags'"
warn  LZ1016  i18next-markup-literal  locales/en.json:3:14  en  accept

  The tag </1> cannot lower to a markup argument, so every tag in this value was escaped to literal text, which is what i18next's t() rendered.

  fix  a tag lowers when its name starts with a letter, it carries no attributes and it is closed, <link>...</link> or <br/>: name a numbered tag and move attributes to the call site.
```

`m.accept()` renders `I accept the <1>terms of service</1>` under both modes. The default mode
says nothing about it, because the parser never reads `<1>` as a tag and the value needed no
escaping. The fix is a named tag, `<link>terms of service</link>`, which lowers to a handler the
way `<b>` does.

## The first build

| Code | Rule | Default |
| --- | --- | --- |
| LZ1012 | `i18next-nesting-unsupported` | error |
| LZ1013 | `i18next-format-unsupported` | error |
| LZ1014 | `plural-suffix-orphan` | warn |
| LZ1016 | `i18next-markup-literal` | warn |
| LZ1017 | `i18next-context-detected` | warn |
| LZ1020 | `icu-in-i18next-file` | warn |

`LZ1015 meta-orphan` sits in the same range and belongs to the description sidecar rather than
the import path; [Catalogs](/guides/catalogs/) covers it.

Warnings alone never fail a build; `--max-warnings` has no cap unless you set one. The rule an
imported catalog usually meets first is `LZ3012 ambiguous-source`: it ships at `warn` and fires
wherever two keys share text and neither has a description, so on a catalog with no descriptions
that is every shared "Save". `loclizr init` on an existing catalog leaves the rule alone and
writes the hardening line commented out:

```ts title="loclizr.config.ts (written by init on an existing catalog)"
  // Turn this on once locales/en.meta.json describes your keys. It
  // reports keys that share source text where at least one of them has no
  // description, so on a catalog imported without descriptions it fires on
  // every shared string at once.
  // severity: { 'ambiguous-source': 'error' },
```

<Aside type="tip">
A file converted to ICU can sit next to files that are still i18next, since the format is per
file. Convert the file that needs a select or a formatted number, leave the rest.
</Aside>

## Migrating an app

There is no codemod. The catalogs are read in place; the call sites are swapped by hand, and
both libraries stay installed until the last one is gone.

<Steps>

1. Point `catalogs` at the existing files, leave `catalogFormat` at `'auto'`, and run
   `npx loclizr build --reporter json`.
2. Group the diagnostics by `file` and `code`. Fix every `LZ1012` and `LZ1013` in the catalog:
   inline the nested text, name the number style in `formats` and write the ICU form, flatten a
   dotted placeholder to one name.
3. Pick `i18nextMarkup`: `'tags'` if the app used `Trans`, otherwise leave the default.
4. Convert the files that need ICU (a select, a formatted number, a context suffix) one at a
   time. A converted file sits beside files still in i18next form.
5. Swap call sites component by component. i18next keeps serving the components not yet moved.
6. Keep i18next installed until `summary.errors` is `0` and every `useTranslation` is gone.
7. Add `npx loclizr check` to CI.
8. Remove the i18next backend and its bundle last.

</Steps>

| i18next | loclizr |
| --- | --- |
| `t('ns:key')` | `m.ns_key()` |
| `t('key', { count })` | `m.key({ count })` |
| `useTranslation('common')` | `m.common_*`, imported from the barrel |
| `<Trans i18nKey="terms">` | `<Parts of={m.terms({ ... })} />` with `i18nextMarkup: 'tags'` |
| `t('key', { returnObjects: true })` over an array | no equivalent; an array value is `LZ1010` |
| `defaultValue` in code | the catalog only; the source text lives in `en.json` |
