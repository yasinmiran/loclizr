## Does switching language need a reload?

No. The locale is read when a message function is called, not when the module loads. `setLocale`
updates one store and notifies subscribers; a root keyed on `useLocale()` remounts with every
string recomputed, and a component that passes `{ locale }` per call re-renders in place and keeps
its state. [Language switching](/guides/language-switching/) shows both on one page.

## Can a message take values I only know at run time?

Yes, that is what arguments are. `m.cart_items({ count })` takes a number and picks the plural
branch at call time, and the type of `count` is checked where you call it. What is fixed at build
time is the set of messages and the shape of each one, not the values that flow through them.

## Can I pick the message itself at run time?

From a set the build knows, yes. `groups: { errors: 'errors' }` generates a record and a key
union, so `errors[code]({ seconds })` is typed, and a code outside the union is a type error.

The cost is that a dynamic call has to pass the union of every member's arguments, and the build
warns when the members disagree. [Dynamic keys](/guides/dynamic-keys/).

## What about CMS content, or text a user typed?

Not a message. A string that does not exist when `loclizr build` runs cannot be checked, typed or
recorded, and formatting it at run time would need an ICU parser in the browser, which the
generated code promises never to ship. A runtime `format()` entry is deferred; see the
[Roadmap](/project/roadmap/).

## Do I have to rewrite my i18next JSON?

No. Point `catalogs` at the files, and each file is classified on its own: `{{name}}` and plural
suffixes mark it as i18next and it is converted in memory, never written.

Nesting with `$t(` and inline formatters are reported rather than converted, and context suffixes
are detected with the rewrite printed for you. i18next keeps running while you look. [Importing
i18next catalogs](/guides/i18next-import/).

## Is there a bundler plugin?

No, and there is no AST pass over your code. `loclizr build` writes ordinary ESM into `src/loclizr`
and your app imports it. The example app keeps a small plugin in its own `vite.config.ts` that
reruns `build` when a catalog changes, and that is a convenience for the edit loop, not a
transform.

## Next.js, React Server Components, React Native?

The generated code imports nothing from any framework, so it runs in all three. What is tested is
React on Vite. Server rendering covers Web Fetch handlers, with a headers primitive for Express and
Fastify; the Next.js App Router is not a first-class target in v0.1 and there is no example.

`loclizr/react` emits no `'use client'` directive, so add your own where a boundary is needed. On
React Native the store works with no `document`; Hermes on Android needs the `intl` build, since
the generated code calls `Intl.PluralRules`, `Intl.NumberFormat` and `Intl.DateTimeFormat`.

## Cannot find module './loclizr/messages' (TS2307)

```text
src/App.tsx(4,20): error TS2307: Cannot find module './loclizr/messages' or its corresponding type declarations.
```

The generated tree has not been built yet: a fresh clone, a teammate's checkout, an editor opened
before the first build, CI before the first build. Run `npx loclizr build`. The `predev`,
`prebuild` and `pretypecheck` scripts `init` prints stop it recurring, since each regenerates the
tree before the command that imports it.

## Will one missing translation fail my build?

`loclizr build` reports it as an error and exits 1, and still writes the generated tree with that
message filled from the fallback chain, so your typecheck keeps working while you fix it. In
`predev` and `prepare` the documented wiring is `build --no-fail`, which prints the same
diagnostics and exits 0 once output is written, so a dev server starts. The gate is
`loclizr check` in CI, which takes no such flag.

So yes: one untranslated key fails `prebuild`, and that is the default and the point. A team whose
translators work after the merge re-levels it, `severity: { 'missing-translation': 'warn' }`, and
has chosen a reminder over a gate; [Translation workflow](/guides/translation-workflow/) has what
that costs.

## Can I turn a check off?

Any rule except three. `severity: { 'unused-message': 'off' }` in `loclizr.config.ts` takes a rule
by name or code to `off`, `warn` or `error`.

`config-invalid`, `outdir-unsafe` and `output-unwritable` cannot be re-levelled, because turning
them down would let the tool do something it must never do quietly. Warnings alone never fail a
run unless you pass `--max-warnings`.

## What is the context record for?

Whoever translates next. Per message it carries:

- the canonical source text and a hash of it
- the argument names and types
- the plural or select shape
- the description and placeholder notes you wrote
- the file and enclosing function where the message is used
- per-locale status

`build` writes it beside the catalogs, you commit it, and `check` compares the committed copy
against what the tree now produces, so a string edit and its context land in the same pull
request or the pull request fails.

## How is that different from a TMS agent that writes context?

Properties, not ownership. An agent that reads your repository per run produces different text each
time, bills per run, stores the result in a vendor database, and arrives after code review. The
record is the same bytes for the same inputs, costs nothing per run, lives in git, and is reviewed
with the diff. It also stays yours when you change vendors.

## Should the generated files be in git?

By default no. `build` writes a self-ignoring `.gitignore` inside `src/loclizr`, and the
`prepare`, `predev`, `prebuild` and `pretypecheck` scripts that `init` prints keep a fresh clone
working.

The file that belongs in the pull request is `locales/loclizr.context.json`. A team that prefers
to commit the tree deletes that one `.gitignore`, and `check` then starts comparing those files
too.

## Does the compiler ever write my catalogs?

Never. Catalogs and the meta sidecar are read. The generated tree and the context record are
written, and `build` deletes only files under `outDir` that carry its own generated header; a file
without the header is reported and left alone.
