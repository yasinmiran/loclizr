Every library on this page works, has users, and does at least one thing loclizr does not. The
research this project came out of spent more time on their strengths than on their gaps, and the
table keeps that balance. Figures are left out on purpose: download counts in this category are
inflated by CI traffic, and none of the claims below depend on one.

## Side by side

| | Model | Checks | Context | Build integration | Choose it when |
| --- | --- | --- | --- | --- | --- |
| **i18next / react-i18next** | Runtime catalog loader, hooks, its own message format with ICU as a plugin | Opt in via `i18next-cli`, which exits non-zero on missing keys | None built in; a TMS or `saveMissing` closes the loop | None required, which is its whole adoption story | You need copy to change without a deploy, you run across many frameworks, or you are already productive in it |
| **next-intl** | Runtime by default with opt-in precompile, request-scoped config, routing and middleware in the box | Runtime fallback on a missing key; no build gate | PO catalogs recommended for file references and descriptions | Next.js App Router, deeply | You are on the App Router today and want routing, negotiation and RSC solved by one package |
| **Paraglide** | Compile to typed ESM message functions, one per message | No `check` command | Left to a separate editor and a VS Code extension | A Vite plugin that owns the build; per-locale output where it can own the whole app build | You want per-locale delivery and you are on a metaframework whose build it can own, SvelteKit first |
| **Lingui** | Macros erased at build, source text as key, ICU generated for you, PO catalogs | `extract` and `compile`, opt in | PO `file:line` and placeholder names | A Babel or SWC plugin over your source | You want extraction from JSX and natural-language authoring, and your toolchain is stable enough to carry an AST transform |
| **FormatJS / react-intl** | Runtime ICU with the most complete implementation, optional precompile | `eslint-plugin-formatjs` on the code side, twenty-plus rules | `description` per message, optional | An extractor CLI, plus a plugin if you want IDs injected | You round-trip catalogs through a TMS that speaks ICU, or you format content the build never saw |
| **Intlayer** | Per-component content files, generated strict types, build-time errors on missing locales | `content test` as a PR gate, plus build-time errors | Context passed to its AI translator as configuration | Its own build artifact, five frameworks | You want library, TMS, CMS and translation in one product and per-component colocation |
| **loclizr** | Compile JSON catalogs to typed ESM, one module per key segment | Fifty-six rules in the build itself, no flag to turn the set off | A deterministic per-message record, committed, gated by `check` | None, at the cost of a build step and generated files | Read on |

## Where loclizr sits

Typed functions are parity with Paraglide, Lingui and Intlayer. The generated shape differs, one
module per top-level key rather than one file per message, and the code is plain ESM with no
plugin, but the developer-facing win is the same one those three already deliver.

Checks are where the claim is about the default. `i18next-cli`, Intlayer's `content test` and
`@lingual/i18n-check` are each a real gate, and each is a separate invocation. Here the gate is
the same command that generates the code, and `check` in CI fails on a stale generated tree or a
stale record as well as on the catalogs.

Context is where the claim is about the artifact. Intlayer hands context to its own translator as
configuration. PO catalogs carry file references when the extractor writes them. Crowdin's agent
reads your repository and writes context per run. loclizr's record is a build output, a pure
function of the tree with no per-run cost, diffed in the same pull request as the string edit, and
readable by any translator or tool. Intlayer is the nearest existing design to this one, and the
difference between them is exactly that sentence plus the absence of a per-component authoring
layer.

## When to choose them

- **Copy has to change in production without a deploy.** i18next, with a backend. loclizr treats
  catalogs as a build input and will not do this.
- **You need one locale's strings per request.** Paraglide, where it can own the build. loclizr
  inlines every declared locale into every message function.
- **Next.js App Router with routing and RSC handled for you.** next-intl. loclizr's Next entry is a
  v0.2 question and there is no example today.
- **Strings are still literals in your JSX and you want them pulled out.** Lingui or Intlayer.
  loclizr has no extractor and no codemod in v0.1.
- **Content unknown at build time.** FormatJS or i18next. A runtime `format()` is deferred past
  v0.1 here because it would ship a parser.
- **A track record.** Any of them. This is a day-zero project, and
  [continuity](/project/continuity/) says what that means in practice.

<Aside type="note">
Maintainer count is one or two for most libraries in this category, including this one. It is
not a differentiator in either direction, and it is the loudest signal in the research about why
libraries die, which is why this project writes its own situation down rather than implying it.
</Aside>
