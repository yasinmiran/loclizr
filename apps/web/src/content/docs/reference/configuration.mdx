Configuration is optional. With no config file at all, `loclizr build` expands
`locales/{locale}.json`, takes `en` as the source locale if an `en.json` exists, and writes
`src/loclizr/`. A config file exists to change one of those or to switch on the things that have no
sensible default, groups and format styles among them.

```ts title="loclizr.config.ts"
import { defineConfig } from 'loclizr'

export default defineConfig({
  locales: ['en', 'de', 'de-AT'],
  sourceLocale: 'en',
  groups: { errors: 'errors' },
  severity: { 'ambiguous-source': 'error' },
})
```

`defineConfig` is an identity function that exists for the type. The file must export the
configuration as its default export, resolved rather than as a promise. Discovery at the project
root tries `loclizr.config.ts`, `loclizr.config.mts`, `loclizr.config.js` and `loclizr.config.mjs`
in that order and stops at the first one; `--config <path>` names one explicitly. TypeScript
configs load through `jiti`, so no build step sits in front of the build step. Since the file is
arbitrary JavaScript, every field is re-checked at load time whatever its declared type says, and
a field that fails is `LZ1001 config-invalid`, exit 2, with a pasteable example in the hint.

Every path in the config is POSIX and relative to the project root, which is the directory the CLI
runs in or `--cwd`. `{locale}`, `{sourceLocale}` and `{ns}` are left as tokens for the reader to
expand.

## Fields

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `locales` | `string[]` | every locale discovered by expanding `catalogs` | The locales to compile. Every message function gets one arm per entry. |
| `sourceLocale` | `string` | `'en'` if discovered, else the single discovered locale | The locale whose catalog defines the message set, the argument types and the end of every fallback chain. |
| `catalogs` | `string` | `'locales/{locale}.json'` | Where the catalogs are. A path with tokens, never a glob. |
| `catalogFormat` | `'auto' \| 'icu' \| 'i18next'` | `'auto'` | How to read each catalog file. `'auto'` decides per file. |
| `i18nextMarkup` | `'literal' \| 'tags'` | `'literal'` | Whether tag-shaped text in an i18next file stays literal text or lowers to markup arguments. |
| `meta` | `string \| false` | `'locales/{sourceLocale}.meta.json'` | The description sidecar, or `false` to switch descriptions off. |
| `outDir` | `string` | `'src/loclizr'` | Where the generated tree is written. Must resolve inside the project root. |
| `record` | `string \| false` | `'locales/loclizr.context.json'` | Where the context record is written, or `false` to write none. |
| `cookie` | `string` | `'locale'` | The cookie name `setLocale` persists to and the server reads. |
| `augmentLocale` | `boolean` | `true` | Whether the generated barrel augments `LocaleRegistry` in `loclizr`, which is what types `useLocale()`. |
| `groups` | `Record<string, string>` | `{}` | Group name to key prefix. Each entry becomes one typed lookup record in `groups.js`. |
| `identifiers` | `Record<string, string>` | `{}` | Catalog key to generated identifier, replacing the mangled one. |
| `fallback` | `'bcp47' \| Record<string, string[]>` | `'bcp47'` | How a locale resolves a message it does not carry itself. |
| `formats.timeZone` | `string` | unset | An IANA zone merged into every date and time format. |
| `formats.number` | `Record<string, IntlOptions>` | `{}` | Named `Intl.NumberFormat` option sets, usable as a style in messages. |
| `formats.dateTime` | `Record<string, IntlOptions>` | `{}` | Named `Intl.DateTimeFormat` option sets. |
| `scan.include` | `string[]` | `['src/**/*.{ts,tsx,js,jsx,mts,mjs}']` | Globs for the usage scan. |
| `scan.exclude` | `string[]` | `['**/node_modules/**', '**/dist/**']` | Globs the scan skips. `outDir` is always added. |
| `severity` | `Partial<Record<RuleName, Severity>>` | `{}` | Rule name to `'off'`, `'warn'` or `'error'`. |

`IntlOptions` is `Readonly<Record<string, string | number | boolean>>`, the shape `Intl` takes.

## Locales and the source locale

With `locales` unset, the locale set is whatever expanding `catalogs` finds, sorted. With it set,
every entry must be a tag `Intl.getCanonicalLocales` accepts, or the build stops with
`LZ1002 locale-tag-invalid`. A declared locale with no catalog file is `LZ1005 catalog-missing`,
an error that still emits, since every message of that locale falls back to source text. A catalog
file for a locale not in the list is `LZ1006 catalog-undeclared` at warn and the file is ignored.

`sourceLocale` is inferred when unset: `en` if an `en.json` was discovered, otherwise the single
discovered locale, otherwise `LZ1004 source-catalog-missing`, whose hint is a `locales` block to paste, one line
per discovered locale with the file it came from. It has to be one of `locales`, because every fallback chain ends there; a source locale
the list does not declare is `LZ1001`.

One more check runs over the list. A declared locale carrying a region subtag whose base tag is
not also declared, `de-AT` without `de`, is `LZ1018 locale-base-missing` at warn. Runtime matching
truncates subtags, so a browser sending `Accept-Language: de` would otherwise get English and
nothing would say why.

## `catalogs`

A path with tokens. It must carry exactly one `{locale}`, at most one `{ns}`, and no
`{sourceLocale}`; anything else is `LZ1001`. Glob characters are rejected for the same reason, with
a hint naming the character, because a token expands to exactly one path segment or one basename
stem and never crosses `/` or `.`. That is what keeps `en.meta.json` and `loclizr.context.json`
out of the locale set, and on top of the pattern, discovery excludes the resolved `meta` and
`record` paths outright.

With `{ns}` in the pattern, `'public/locales/{locale}/{ns}.json'` matches the layout
`i18next-fs-backend`, `i18next-http-backend` and `next-i18next` default to. One file is one
catalog, and every key from it is prefixed with the namespace: `common.json` holding `nav.home`
produces the key `common.nav.home`. Under that layout with `locales` unset, the discovered
directories are the locale set, and `Intl.getCanonicalLocales('shared')` does not throw, so a
stray `locales/shared/` would declare a locale called `shared`. Declaring `locales` is the fix, and
a split-catalog project should do it anyway.

## `catalogFormat`

The format is decided per file, never per project and never per value. Under `'auto'`, each
catalog is classified after flattening and before any conversion: the file is i18next when any
string value contains `{{`, or when any key carries a CLDR plural suffix that would fold
(`X_one` beside `X_other`). Otherwise it is ICU. `'icu'` and `'i18next'` force every file and skip
the classification.

There is no hybrid parse. ICU argument syntax inside a file read as i18next is literal text, which
is what i18next itself rendered, and `{{name}}` inside a file read as ICU is a literal brace around
an argument. The one mistake `'auto'` can make invisible, `{count, plural, ...}` written into a file
that classified as i18next, is the one it reports: `LZ1020 icu-in-i18next-file`, whose hint names
the `{{` or suffixed key that decided the classification.

## `i18nextMarkup`

Applies to files read as i18next only. At `'literal'`, tag-shaped text such as `<b>here</b>` is
escaped so it stays text, and each value that needed it raises `LZ1016 i18next-markup-literal` so
the conversion is visible. At `'tags'`, `<` is taken out of the escape set for the whole catalog
set and those tags lower to markup arguments, which changes the affected message's return type from
`string` to an array of parts and makes each tag a required handler at the call site.

## `meta`

A JSON file, flat-key addressed, source locale only, holding a `description` and a `placeholders`
map per key. The path takes `{sourceLocale}`. An entry for a key the source catalog does not have is
`LZ1015 meta-orphan`. `false` switches descriptions off entirely; `LZ3012 ambiguous-source` and
`LZ5006 missing-description` then hint at setting `meta` rather than at editing a file.

## `outDir`

Must resolve inside the project root, or the run is `LZ1007 outdir-unsafe`, exit 2. The same
check runs again at write time through symlinks, and a path that escapes that way is
`LZ5001 output-unwritable`. The reason is the prune step: `build` deletes files under `outDir`
that carry the generated header and that this emit did not produce, so the directory has to be one
the project owns. `outDir` may not contain the resolved `catalogs`, `meta` or `record` path either
(`LZ1001`), because the tree writes a self-ignoring `.gitignore` into it and the catalogs would stop
being committed.

## `record`

The context record's path, taking `{sourceLocale}`. `false` writes no record and skips
`LZ5003 record-stale` and `LZ5007 record-rewritten`, which have nothing to compare.

## `cookie`

An RFC 6265 cookie name: letters, digits and the punctuation ``!#$%&'*+-.^_`|~``, nothing else. A name outside that
set would be written into `document.cookie` verbatim and never read back, so the loader rejects it
as `LZ1001`. The generated `_locale.js` passes the name to `$configure1`, `setLocale` writes it, and
the client reads it first when detecting the initial locale. `loclizr/server` takes the name
separately in `NegotiateOptions`, since the server entry never reads the generated tree.

## `augmentLocale`

Controls one block in `messages.d.ts`:

```ts
declare module 'loclizr' {
  interface LocaleRegistry {
    locale: AppLocale
  }
}
```

That augmentation is what makes `getLocale()`, `useLocale()` and `setLocale()` from the `loclizr`
package take and return the union of your locales rather than `string`. Two generated directories
in one TypeScript program both declaring it is TS2717, "Subsequent property declarations must have
the same type", reported inside generated files, and the app stops compiling. Set it `false` in the
second tree. The barrel keeps its own concrete `getLocale`, `setLocale` and `locales` declarations
either way, so `m.getLocale()` stays typed. `loclizr init` sets it `false` for you when it finds an
existing generated tree in the workspace.

## `groups`

Maps a group name to a key prefix. `{ errors: 'errors' }` collects every key under `errors.` into a
frozen record exported from `groups.js` as `errors`, with a `Readonly<{ [K in ErrorsKey]: ... }>`
type so `errors[code]` is checked against the member's real arguments. A prefix matches on a dot
boundary: `err` does not capture `errors.forbidden`. A prefix that matches nothing is
`LZ4004 group-empty`, and a group whose members do not share one argument set is
`LZ4006 group-args-heterogeneous`, since a dynamic call then has to pass the union.

The group name becomes both the export identifier and, PascalCased, the base of the `ErrorsKey` and
`ErrorsArgs` type names. Two groups sharing either is `LZ4001 identifier-collision`.

## `identifiers`

Maps a catalog key to the identifier its message function gets, replacing the mangled form
entirely. It exists so a collision can be fixed without renaming a key that i18next is still
reading during a migration:

```ts
identifiers: { 'nav.home': 'navHome' }
```

The value is validated the same way a mangled identifier is: it must start with an identifier
character, not be a reserved word, `default` or `then`, and not enter the `$` namespace or the set
the barrel already exports (`locales`, `sourceLocale`, `getLocale`, `setLocale`, `subscribe`). An
entry can also rename a top-level key segment, which is the fix when one mangles to `_locale`,
`_formats` or `_root`, or when two segments differ only by case and a case-insensitive filesystem
would merge their modules.

## `fallback`

Every locale gets its own compiled arm in every message, so fallback is resolved at build time,
per message, and the runtime never walks a chain. What `fallback` sets is the middle of that
chain.

`'bcp47'`, the default, gives `[L, ...declared BCP 47 truncations of L, sourceLocale]`, so `de-AT`
resolves through `de` and then `en`. A `de-AT.json` holding twelve overrides on top of a complete
`de.json` is a valid catalog rather than a few hundred errors; those twelve are `translated`, the
rest are `inherited`, and only falling all the way through to the source locale is a missing
translation.

A map replaces the middle for the locales it names and leaves the rest on truncation:

```ts
fallback: { nb: ['no'] }
```

Keys that are not valid locale tags are dropped silently, since they could never be declared
locales. The source locale is always the last step whether or not the list names it.

## `formats`

Named format styles beyond the ones ICU defines, keyed by the name a message uses:

```ts
formats: {
  timeZone: 'UTC',
  number: { compact: { notation: 'compact', maximumFractionDigits: 1 } },
  dateTime: { weekday: { weekday: 'long', month: 'long', day: 'numeric' } },
}
```

A message then writes `{views, number, compact}` or `{when, date, weekday}`. A style a message
names that is neither built in nor here is `LZ2002 icu-style-unknown`. Each option set is handed to
`Intl.NumberFormat` or `Intl.DateTimeFormat` at load time, with a fixed probe locale so the verdict
is the same on every machine, and one `Intl` rejects is `LZ1001` with `Intl`'s own message as the
hint. Otherwise the first thing to throw would be every date message at once, in the viewer's
browser.

`timeZone` is merged into every resolved date and time option set. It exists because an ICU
skeleton can carry `timeZoneName` and never an IANA zone, so without this field the only way to
pin one would be rewriting every date message in every catalog. Leave it unset in a browser SPA,
where the viewer's own zone is the right one; set it where the server renders dates and both sides
of the hydration boundary must agree. While it is unset, `LZ3011 date-without-timezone` is
available at `off` for a project that wants to be told which messages format a date without one.

## `scan`

The usage scan reads every file `include` matches minus `exclude`, and minus `outDir` whatever
`exclude` says, since generated files reference their own identifiers. It binds a generated module
by import specifier suffix (`./loclizr/messages`, `@/loclizr/messages`, `#app/loclizr/groups` all
bind, with no resolver and no alias map read) and records every `m.<id>` access and every bound
bare call. What it finds lands in the record's `usage` field, and nothing it finds can fail a build
by default: `LZ5004 scan-found-nothing` is `warn` and fires only when files were read and none
imported the generated tree, `LZ5005 unused-message` is `off`, and the record gate compares with
`usage` projected out.

## `severity`

Re-levels any rule to `'off'`, `'warn'` or `'error'`, keyed by rule name, the one printed beside
each code:

```ts
severity: {
  'ambiguous-source': 'error',
  'missing-translation': 'warn',
  'unused-message': 'error',
}
```

A name that is not a rule is `LZ1001`. Three rules cannot be re-levelled at all, and naming one
of them in `severity` is itself `LZ1001`:

| Code | Rule | Why it is fixed |
| --- | --- | --- |
| `LZ1001` | `config-invalid` | Turning it down is self-referential: the field that turns it down is the one it validates. |
| `LZ1007` | `outdir-unsafe` | Turning it down would let a build write outside the project root and exit 0. |
| `LZ5001` | `output-unwritable` | The build could not write what it produced, and nothing downstream can act on a tree that is not there. |

Those three are also the only rules that exit 2.

<Aside type="caution">
Re-levelling changes the printed severity and nothing else about a fatal rule. `LZ4001
identifier-collision` at `warn` still blocks emission: the run prints the collision as a warning,
writes no tree, and exits 1, because a run that could not produce output never exits 0. Fatality
decides whether a tree is written, and it is not on this dial.
</Aside>

`severity` is read once, at the end of the run, by the reporter. No analysis module reads it to
decide whether or at what level to raise a diagnostic, which is why a re-levelled rule cannot
change what the compiler emitted. One rule reads one key to write a sentence: `LZ3012`'s hint names
the severity the rule is not already running at.

## Runtime and server settings that are not here

Nothing in this file reaches the browser. The generated `_locale.js` carries `locales`,
`sourceLocale` and `cookie` into the runtime through `$configure1`, and that is the whole handoff.
`loclizr/server` functions take their locale list explicitly in `NegotiateOptions`, so a server
entry that never imports the generated tree still negotiates correctly.
